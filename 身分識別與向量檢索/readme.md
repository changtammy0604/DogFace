# **身分識別與向量檢索**

### **[統整與網站呈現在這裡](https://colab.research.google.com/drive/1CiR876it15IIzQbYLcuGyMeLupYrstPX?usp=sharing)**

本部分透過計算使用者上傳的犬隻特徵向量與資料庫內的特徵向量之餘弦相似度，分別針對身體與臉部，各挑出最相近的前十名。
  
**(一)　系統資料庫**

使用 Supabase 雲端資料庫服務，系統資料庫選用 PostgreSQL 配合 pgvector，pgvector 提供 "<=>" 運算子計算兩向量間的餘弦距離，餘閒距離與餘弦相似度的轉換公式為：
$$
Cosine Distance = 1 - Cosine Similarity
$$

**(二) 資料庫之建立**

本資料庫整合了四個不同的資料來源：

1. 政府流浪狗資料庫[5]（每日 API 同步）：收容所內待認養之犬隻。
2. 政府飼主報失資料[6]（每日 API 同步）：民眾向政府登記走失之犬隻。
3. 網站使用者拾獲上傳：民眾拍攝之街頭遊蕩犬隻。
4. 網站使用者協尋上傳：飼主自行上傳之愛犬走失紀錄。
   
為統一不同格式之資料，資料庫以以下內容作為標籤：

1. id、gov_animal_id：系統主鍵與政府原始資料庫之唯一識別碼。
2. source_type：標記前述之四大資料來源，作為混合檢索之過濾標籤。
3. status：犬隻目前狀態（如：走失、尋獲、收容中）。
4. metadata：品種、毛色、特徵描述、通報地點與時間戳記。
5. image_url：影像連結。
6. face_embedding、body_embedding：犬隻面部、身體圖片之特徵向量。

**(三) 影像過濾與防呆機制**

政府端開放資料常包含非犬隻影像（如貓、禽鳥），或有預設佔位圖而產生無效圖片連結。 為此，本系統於爬蟲抓取階段實作了過濾機制，確保抓取的圖片為有效之犬隻圖像：
 
1. HTTP 狀態與標頭驗證：確保伺服器回傳碼為 200 OK，且 ContentType 確為影像格式
2. 位元組容量過濾：經實證分析，政府系統回傳之查無圖片等錯誤網頁，其檔案大小通常落於數百 bytes，而解析度極低但具備實質影像結構之 JPEG 檔，大小不低於 1.5 KB。因此，系統設定 1500 bytes 為下限，凡低於此閾值之檔案皆判定為無效封包，直接於記憶體中捨棄，確保後續進入管線之資料皆具備特徵萃取價值。


**(四) 資料庫同步**

在同步政府資料庫的方式上，本研究針對增量更新 (Delta Check)與全量更新 (Full Upsert)進行架構評估。增量更新需於程式端預先載入資料庫現有之 ID 清單，經由記憶體比對後僅寫入變動資料，此舉雖可降低資料庫I/O，但考量到此研究核心為視覺比對演算法，且最終清洗後之單批有效資料量落於數千筆，本系統最終採用全量更新策略，並設 gov_animal_id 為唯一鍵，每日更新。

# **網站呈現**
本系統採用 Gradio 框架搭建前端介面，整合後端資料庫與系統辨識模型，將整體系統運作與最終成果呈現分為以下機制：

**(一) 檢索分流設計**

當使用者選擇上傳遺失犬隻時，系統會自動將上傳照片與政府收容所（GOV_STRAY）資料進行特徵比對；若情境為撿到犬隻，則切換比對至政府民眾遺失登記（GOV_LOST）資料。排除無效檢索目標並大幅縮小運算範圍，提升效率與精準度。

**(二) 自動化資料同步**
為確保系統資料之即時性，後端資料庫整合 GitHub 自動化排程服務。每日定時觸發工作流程，透過分頁機制向政府開放 API 抓取完整最新名單，比對並自動下架已尋獲或被領養之舊資料。隨後，系統運行特徵提取模型獲得新進犬隻之特徵向量，並同步至 Supabase 雲端資料庫。
